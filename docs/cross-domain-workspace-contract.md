# 跨模块工作空间与动作授权契约（草案）

## 目标

本契约统一产品开发、Listing、知识库与 AI Job/Run 的访问范围。原则是：**工作空间定义数据边界，资源归属定义可见范围，动作权限定义可执行操作，审计日志记录关键变更。**

## 统一请求上下文

每个受保护请求都必须以如下范围对象运行，任何字段缺失均不得降级为跨工作空间查询。

| 字段 | 来源 | 约束 |
|---|---|---|
| `workspaceId` | 当前用户的默认工作空间或显式已校验切换 | 必填；所有查询、写入、Artifact、Job 必须携带 |
| `actor` | 已认证用户、角色及工作空间成员资格 | 必填；用于动作授权与审计 |
| `projectId` | 请求路径或输入 | 可选；存在时必须属于 `workspaceId` |
| `resource` | 项目、文件、知识条目、Agent Run、Job 或 Artifact | 必填；必须验证其工作空间和所属关系 |
| `action` | `read`、`create`、`update`、`confirm`、`run`、`cancel`、`export`、`delete` | 必填；按角色、资源与动作判断 |

## 领域资源范围

| 领域 | 范围根 | 写入前校验 | 下游产物与任务要求 |
|---|---|---|---|
| 产品开发 | `devProject.workspaceId` | 项目属于当前工作空间且具备编辑权限 | 生成 Job、阶段快照、Artifact 使用同一工作空间与项目 |
| Listing / 图片 | `project.workspaceId` | 项目读写授权与工作空间一致 | Agent Run、Step Artifact、图片 Job 固定回写同一项目范围 |
| 知识库 | `knowledgeItem.workspaceId` 或团队共享范围 | 读取遵循共享策略；写入需创建/编辑动作权限 | 被引用时记录来源工作空间和消费记录，禁止隐式跨空间拼接 |
| AI Job / Run | `aiJob.workspaceId` 与 `projectId` | 创建、取消、重试、确认均检查当前用户对关联项目或资源的动作权限 | Job、Agent Event、Artifact Consumption 与审计日志使用同一工作空间 |

## 动作权限矩阵

| 动作 | 普通运营人员 | 管理者 | 超级管理员 | 必须审计 |
|---|---|---|---|---|
| `read` | 已分配或团队共享资源 | 工作空间内全部 | 工作空间内全部 | 否 |
| `create` / `update` | 已授权项目或本人资源 | 工作空间内全部 | 工作空间内全部 | 是 |
| `confirm` | 已授权项目的人工审核节点 | 工作空间内全部 | 工作空间内全部 | 是 |
| `run` / `retry` / `cancel` | 已授权项目关联 Job | 工作空间内全部 | 工作空间内全部 | 是 |
| `export` | 已授权且非受限资源 | 工作空间内全部 | 工作空间内全部 | 是 |
| `delete` | 不允许删除他人资源 | 工作空间内全部，受保护资源需二次确认 | 工作空间内全部，受保护资源需二次确认 | 是 |

## 当前审计结论

运营领域已通过 `workspaceProcedure` 在路由层统一检查工作空间、动作权限和写入审计。Listing 领域已有项目级访问校验与工作空间上下文；AI Job/Run 已保存 `workspaceId` 并在关键任务操作中写入审计。产品开发和大部分知识库路由仍直接使用基础受保护过程，尚未完全统一到同一动作授权中间件。

## 分阶段收口建议

1. 建立 `workspaceScopedProcedure`，将现有运营中间件抽为平台公共能力；产品开发、Listing、知识库与 AI Job 路由统一接入。
2. 为所有项目、知识、文件、Job 和 Artifact 查询添加“资源工作空间必须等于请求工作空间”的仓储层断言，避免仅靠路由层约定。
3. 将 Job 创建、取消、重试、确认的项目授权检查抽为单一策略；无项目 Job 必须声明受管资源类型与资源 ID。
4. 将跨领域消费统一落入 `Artifact Consumption + Security Audit Log`，记录精确版本、消费者、动作和工作空间。

> 该契约不引入知识库审批节点，也不改变已确认的人工审核、锁定与工作流流转语义。
