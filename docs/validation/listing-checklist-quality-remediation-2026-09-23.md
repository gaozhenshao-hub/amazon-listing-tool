# Listing 五点自检质量与 0/15 评分修复

**日期：** 2026-09-23  
**范围：** 青岛独立站与 Manus 托管站的 Listing 五点自检，以及标题、产品描述、搜索词和 Q&A 自检。  
**执行边界：** 本次未重跑任何用户 Listing、文件、采集或实际模型生成；生产验收仅检查服务、构建入口、模型目录和 Skill 配置。

## 现象与根因

用户截图中的单条五点卖点实际显示为 **247/200–280 字符**，但自检面板却显示 **0/15 通过**。这不是可信的质量判定，而是前端将缺失/不完整的 `checkListScores` 当作完整评分卡来渲染的结果。

只读生产审计证实，两个环境的自检 Skill 存在以下问题：

| 问题 | 影响 | 修复 |
|---|---|---|
| 自检响应未强制完整结构化合同 | 空对象或键名漂移会被保留，界面把 15 项均渲染为未通过 | 新增完整合同校验；少一项、字段类型不符或无法解析时返回明确的“结果格式不完整，未计入评分”错误 |
| 批量自检用旧的 React 状态快照持久化 | 同一批中刚获得的评分可能未进入最终保存负载 | 改为在内存中累积最新结果后统一保存 |
| 高质量自检没有显式使用质量优先路由 | 审计/质量判断可能使用标准模型而非 GPT‑6 Astra | 五类自检入口均传入受治理的 `quality_first` 执行预设；数据库 Skill 的 quality/evaluation 策略均为 `teamo-gpt-6-astra` |
| Q&A 提示词输出键与页面消费键不一致 | `quantifiedData`、`semanticRelations`、`priorityOrdering` 不会映射到页面要求的三个维度 | 统一为 `dataQuantification`、`semanticRelation`、`priorityOrder` |

> 生成质量与自检质量是两条独立链路：本次修复没有把自检分数伪装成生成质量提升，而是确保**只有完整、可追溯、质量优先模型给出的结果**才进入评分面板。用户仍可以编辑、重新生成并重新自检，系统不会自动确认内容。

## 已实施的控制

五类 Listing 自检 Skill 均采用 JSON 草案合同、人工审核、禁止自动执行，并保留其原专业提示词及 Listing 奥美角色策略。每个 Skill 的输出合同要求其完整返回页面实际需要的维度：五点 15 项、标题 10 项、描述 8 项、搜索词 5 项、Q&A 8 项。

当模型响应不完整时，服务器返回可读失败而非空分数；五点面板显示“上次自检结果不完整”，并提供重新自检入口。这样不会误导用户将传输/格式失败理解为内容质量不佳。

## 当前使用方式

1. 对已存在的五点内容，点击 **Check List 自检** 或批量自检。
2. 若显示“上次自检结果不完整”，该结果没有被计分；可点击重新自检。
3. 若需要提高文案内容本身的质量，使用已有的编辑/重新生成操作，并在质量优先模式下进行人工审核后确认。
4. 本次未自动重跑截图中的 Listing，避免在未确认的情况下产生额外模型费用或覆盖用户编辑。
