# 青岛独立站领星定时任务未自动执行：根因复盘

## 根本原因

四个领星任务在数据库中保存为`triggerMode=heartbeat`并关联托管环境的外部Heartbeat任务UID。该设计在托管环境中依靠平台回调触发；青岛独立站没有该平台回调。因此，部署时虽然将任务定义、Cron和“已启用”状态同步到了青岛数据库，但**没有将外部Heartbeat触发器替换为独立站本机可执行的Cron触发器**。

当时青岛的Scheduler只注册情报采集、待办提醒和AI中台的内部任务。内部调度器明确忽略`triggerMode=heartbeat`的任务，因此四个任务未进入Node进程的计划队列。任务中心显示的`nextRunAt`只是迁移来的历史投影，不是本机未来真正会执行的定时器，故会停留在2026-08-27，运行次数也一直为0。

## 证据链

| 层级 | 观察结果 | 结论 |
| --- | --- | --- |
| 任务定义 | 四个任务均为系统托管、已启用、带外部Heartbeat UID、`triggerMode=heartbeat` | “已启用”只代表定义有效，不代表ECS有触发器 |
| 青岛部署 | 初始Scheduler未注册任何领星本机Cron | 外部Heartbeat任务不能在ECS自行触发 |
| 运行审计 | 任务运行次数为0，最后运行为空，下次时间过期 | 没有实际Run进入领星Tool Gateway或数据批次流程 |
| 数据影响 | 每日ASIN、库存、广告及父ASIN周汇总均没有在青岛按计划持续生成 | 青岛数据库只能保留同步前或人工补读的历史数据 |
| 周汇总显示 | 8月17至23日的周汇总批次存在但原规则停在待审批 | 即使日数据已完整，旧的人工审批设计也会阻止周事实进入产品总览 |

## 已实施修复与当前状态

已新增仅在独立站明确开启时运行的`localLingxingScheduler`：它读取已有的四个系统任务投影，使用相同的UTC Cron和任务UID在ECS本机注册定时器，不新建并行任务，也不绕过现有Run、Trace、异常和分页校验。日志已证明四个任务能够被本机注册。

为避免历史补读与日常任务并发，目前Scheduler按用户指示处于暂停状态；广告关键词历史补读也处于暂停状态。当前两周父ASIN周事实已经基于已入库日快照写入，供产品总览使用。

进一步隔离启动验证发现，项目使用的`node-cron 4.2.1`对父ASIN周任务的六段表达式`0 10 8 * * 1`存在下一次匹配计算错误：2026-08-31应投影到2026-09-07 08:10 UTC，却返回2029-01-01。该库的任务Runner亦使用同一个下一次匹配计算来设置唤醒计时器，因此它会使周汇总长期不触发，而不仅是页面显示错误。已将**固定的UTC周一父ASIN汇总**切换为受限本机计时器；每日任务仍继续使用既有node-cron。定向回归确认固定时点下周任务投影为下一自然周。

同时，隔离启动—停止验证确认此前的SIGKILL风险来自共享Drizzle/MySQL连接池在计时器停止后仍持有事件循环，以及LeaderLock连接已不可用时释放锁抛错。当前修复在停止顺序中先清理计时器、再以容错方式释放LeaderLock、最后关闭共享数据库连接池。隔离进程在收到SIGTERM后输出`[Scheduler] stopped`并退出；测试包装器显示124是超时工具向子进程发送TERM后的标准返回码，并非Scheduler再次被systemd SIGKILL。正式Scheduler全程保持`inactive`。

## 防复发措施

恢复自动同步前，应先修复Scheduler优雅退出阶段的资源释放顺序。日志显示其关闭数据库连接后，LeaderLock仍尝试发送心跳或释放锁，导致`Can't add new command when connection is in closed state`，最终由systemd超时后SIGKILL。这个问题不是最初“任务从未注册”的根因，但会降低本机Scheduler重启后的稳定性。

恢复顺序应为：先验证无领星读取的Scheduler启动—停止回归（已完成）；再在用户明确许可后启动正式Scheduler并观察每日任务为次日、周任务为下一周的运行时间推进；最后在一个自然计划窗口后核验Run、Trace、批次和产品总览覆盖。不得用伪造状态或手工修改运行次数替代实际触发。
